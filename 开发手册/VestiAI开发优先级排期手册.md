# VestiAI 开发优先级排期手册

> 本手册只按需求优先级和前置依赖安排开发顺序，不安排日期、工期或具体负责人员。  
> 条目状态按实际验收更新；当前交付状态见文末与 [开发实施记录](VestiAI开发实施记录.md)。
> 详细背景、架构和技术依据见 [VestiAI 项目改进与迭代开发方案](./VestiAI项目改进与迭代开发方案.md)。

## 1. 项目目标与阅读方法

**把 VestiAI 从“自己选衣服、点击生成试穿”，升级成“说出需求，AI 从真实衣橱推荐搭配，并协助试穿”的搭配助理。**

希望完成的用户流程：

**提出穿搭需求 → 查询自己的衣橱 → 获得推荐 → 选择或调整 → 保存搭配／按授权试穿 → 查看真实结果。**

已有的衣橱、图片、SQLite 数据库、网页、macOS App 和百炼模型接口继续复用。第一轮推荐仍限定为“上装 + 下装”或“连衣裙／连体服”，保留原有手动单件试穿。

阅读与执行规则：

1. 先看优先级总览，再按交付批次推进。
2. 同一优先级内，前置依赖决定先后；编号用于追踪需求，不代表工期。
3. 前置需求没有通过验收，依赖它的功能不进入正式交付。
4. 每项需求同时完成必要的数据处理、界面、错误反馈和相关验证，不把“接口写完”当成整项完成。
5. P3 只有触发条件成立时才启动；未触发时不阻挡核心产品交付。

## 2. 优先级总览

| 优先级 | 含义 | 本项目安排 | 完成后得到什么 |
| --- | --- | --- | --- |
| **P0：必须先做** | 保证数据、权限和付费操作可靠 | 数据保护、共享业务能力、防重复生成、恢复、预算和授权 | 新功能可以建立在可靠的现有系统上 |
| **P1：核心产品升级** | 实现搭配助理的主要价值 | 自动推荐、方案卡片、保存与试穿、聊天、工具调用和完成检查 | 用户可以通过按钮或对话完成推荐与试穿 |
| **P2：使用体验增强** | 降低整理成本，提高个性化效果 | 批量入库、审核、失败项处理、长期偏好、反馈和天气 | 更方便建立衣橱，推荐更符合个人习惯 |
| **P3：条件触发的探索** | 解决明确出现的新问题 | 其他试穿引擎对比、必要的长期云部署 | 在证据充分时扩展能力 |

开发主线：

**P0 基础可靠性 → P1 自动推荐 → P1 聊天 Agent → P2 批量整理 → P2 个性化 → 条件满足后再做 P3。**

## 3. P0：基础可靠性需求

这些需求优先处理，是自动推荐和 Agent 能安全调用现有功能的前提。

| 编号 | 需求 | 实现要点与验收标准 | 前置依赖 |
| --- | --- | --- | --- |
| **P0-01** | 数据备份与兼容迁移 | 建立可恢复的 SQLite 和图片备份；新增字段不丢失旧衣物、穿搭和历史；验证旧数据可以继续使用 | 无 |
| **P0-02** | 共享业务函数与统一身份检查 | 网页和未来 Agent 共用衣橱查询、搭配保存、试穿等函数；身份由服务端确定；其他用户的衣物、人物照、任务和文件无法访问 | P0-01 |
| **P0-03** | 防重复生成与付费重试分类 | 同一请求只创建一份本地生成记录；并发重复调用复用记录；分开查询重试与创建任务重试；提交结果未知时不自动重发付费请求 | P0-02 |
| **P0-04** | 任务恢复与未知状态展示 | 有远程任务 ID 时恢复查询原任务；提交中但没有 ID 时显示待核实；不能因应用重启就重新生成或直接宣称任务失败 | P0-03 |
| **P0-05** | 统一模型用量与预算限制 | 覆盖识别、分割、基础／Plus 试穿、推荐和主 Agent 调用；记录用量与费用估算；检查任务、用户及全局上限；未知费用不当成零费用 | P0-02、P0-03 |
| **P0-06** | 服务端费用授权 | 将授权绑定方案、形象照、质量、次数及预算范围；重复调用不能重复消费授权；模型不能自报“用户已确认”；现有访客与 Plus 限制继续生效 | P0-03、P0-05 |

### P0 的交付检查

- 原有衣橱、导入、收藏、搭配、试穿、删除和历史仍可使用。
- 数据迁移失败可以恢复，不能只替换代码后继续写入不兼容数据库。
- 重复点击、重复工具调用和并发请求都不能创建重复的本地试穿请求。
- 模拟远程请求已接收但响应丢失，系统进入未知状态，不自动再提交。
- 模拟重启，能够继续查询已经获得远程 ID 的任务。
- 权限、预算和费用授权不能被网页或 Agent 绕过。

**进入 P1 的条件：P0-01 至 P0-06 完成相应实现和验证，现有功能回归通过。**

## 4. P1：自动推荐与聊天搭配助理

P1 分为两个可独立验收的交付：先交付“帮我搭配”，再交付聊天 Agent。

### 4.1 先做自动推荐

| 编号 | 需求 | 实现要点与验收标准 | 前置依赖 |
| --- | --- | --- | --- |
| **P1-01** | 补齐推荐所需衣物信息 | 增加可编辑颜色、风格和场合标签；旧衣物优先使用已有描述与季节，不强制全部重新识别；缺失信息不编造 | P0-01、P0-02 |
| **P1-02** | 验证并配置推荐／主模型 | 优先百炼；分别验证结构化输出和工具调用；模型名称可配置；样例证明能力可用，不直接假定现有视觉调用已经支持 Agent | P0-05、P0-06 |
| **P1-03** | 自动推荐核心逻辑 | 接收场合、本次偏好、锁定／排除单品和可选手动天气；从本人候选衣物中选组合并解释；优先尝试 3 套，实际不足时如实返回可用数量 | P1-01、P1-02，以及已通过的 P0 |
| **P1-04** | 推荐校验与方案卡片 | 校验真实 ID、用户归属、分类组合、排除条件和重复搭配；显示真实单品图片与理由；模型给出非法方案时拒绝或有限重试 | P1-03 |
| **P1-05** | 保存推荐与连接试穿 | 复用穿搭库及现有试穿；补齐连衣裙／连体服单件方案保存；保存和生成前重新校验单品状态；保留原有手动操作 | P1-04、P0-06 |

这一交付先形成自动推荐功能。它不依赖聊天 Agent，但会调用模型，必须纳入费用提示和预算限制。

### 4.2 再做聊天 Agent

| 编号 | 需求 | 实现要点与验收标准 | 前置依赖 |
| --- | --- | --- | --- |
| **P1-06** | 业务工具与主 Agent 循环 | 开放查询衣橱、读取单品、推荐、保存搭配、提交试穿、查询结果；模型选择工具，程序执行，结果回到模型继续决策；工具共用 P0 的权限与预算 | P1-02、P1-05，以及已通过的 P0 |
| **P1-07** | 聊天入口与本轮上下文 | 用户可以自然语言表达需求；“换一套”保留原场合和未撤销约束；缺少必要信息时询问；未选择形象照时提供选择入口 | P1-06 |
| **P1-08** | 后台结果回传与会话恢复 | 生成返回任务 ID；后台等待结束后将真实结果送回 Agent；等待期间保留目标；页面刷新后恢复会话与执行状态，不反复调用模型询问进度 | P1-07、P0-04 |
| **P1-09** | 完成判断与异常出口 | 依据有效方案、用户约束、任务成功和图片可访问判断完成；只推荐时不自动试穿；达到调用／预算上限时保留进度并说明未完成部分 | P1-08、P0-05、P0-06 |

### P1 的交付检查

- 输入“面试，不穿裙子”，只能推荐本人衣橱内有效的上装与下装。
- 衣橱不足时说明缺少什么，不伪造衣物，不强凑 3 套方案。
- 连衣裙方案可以保存，推荐卡片能进入现有试穿流程。
- “太正式了，休闲一点”会调整方案，并保留原有未撤销要求。
- “换一套”比较实际衣物组合，不用改名字冒充新搭配。
- 只要求推荐，不会生成试穿；一次基础试穿授权不会变成多次或 Plus。
- 只有真实任务成功并存在有效图片，才报告“试穿已完成”。
- 工具失败、预算不足或信息缺失时，给出具体状态和可恢复的位置。

**核心产品交付条件：P0 与 P1 全部通过。此时已经具备模型驱动的行动与结果反馈闭环。**

## 5. P2：批量整理和个性化体验

优先降低建立衣橱的操作成本，再加入长期偏好与反馈。自动天气是增强项，手动天气足以支撑 P1。

| 编号 | 需求 | 实现要点与验收标准 | 前置依赖 |
| --- | --- | --- | --- |
| **P2-01** | 多图批量上传与逐项进度 | 一次选择多张图片，沿用既有格式与大小限制；每张图片独立记录进度和错误；控制同时处理数量，复用后台任务 | 已通过的 P0；主交付顺序在 P1 之后 |
| **P2-02** | 待审核、去重提示与确认入库 | 支持修改识别结果并选择确认；待审核条目不参与正式推荐；哈希相近只提示，不强制合并不同实物；重复确认不重复入库 | P2-01、P1-04 |
| **P2-03** | 批量失败项处理与取消 | 部分失败不影响成功项；只处理需要重试的步骤；提交未知沿用核实流程；取消后不再提交新任务，已提交任务单独显示状态 | P2-02、P0-03、P0-04 |
| **P2-04** | 显式长期偏好 | 保存用户明确设置的颜色、风格和类别偏好；支持查看、修改和删除；本次要求与长期偏好分开，当前指令优先 | P1-07 |
| **P2-05** | 推荐反馈与排序改进 | 记录喜欢／不喜欢和可选原因；用可解释规则调整推荐；删除偏好／反馈后不继续影响新推荐；用户之间隔离 | P2-04、P1-03 |
| **P2-06** | 自动天气辅助 | 用户选择城市，获取天气并显示来源与数据有效性；查询失败回退到手动信息，不编造实时天气 | P1-03；不阻挡其他 P2 项 |
| **P2-07** | 实际穿着记录（可选） | 用户主动记录真正穿过的搭配；与试穿生成历史分开；有实际需求后再增加相关统计 | P2-05 |

### P2 的交付检查

- 一批照片中某张失败，其他照片仍可审核和入库。
- 同一批次重复提交或确认，不增加重复正式单品。
- 已成功的收费步骤不会因为重试整批而重新执行。
- 原图与真实裁剪图被保留，不用生成式展示图代替实物证据。
- “这次不穿裙子”不会变成以后永远不推荐裙子。
- 用户可以管理自己的长期偏好和反馈；当前要求可以覆盖旧偏好。
- 生成过试穿图不被自动标记为实际穿过。

## 6. P3：有条件才启动的探索

P3 不作为完成衣橱 Agent 的必要条件。先确认问题，再决定是否投入。

| 编号 | 需求 | 启动条件 | 实现与验收要点 |
| --- | --- | --- | --- |
| **P3-01** | CatVTON 对比实验 | 现有百炼在效果、成本或使用条件上出现明确问题；许可、硬件与实验费用范围明确 | 独立服务运行，用相同人物与衣服比较细节、人物一致性、成功率及资源消耗；先验证单件与组合兼容性 |
| **P3-02** | OOTDiffusion／IDM-VTON 备选实验 | P3-01 无法满足已确定的需求，且备选实验条件成立 | 用同一组样例比较，再选择一种方案；不同时维护三种引擎 |
| **P3-03** | 其他试穿引擎接入 VestiAI | 对比结果证明有价值，并满足目标用途的许可要求 | 通过统一试穿入口接入；保持百炼可用；失败不破坏原有数据和历史 |
| **P3-04** | 长期云部署与数据持久化 | 明确需要长期在线使用，而非现有短期演示 | 落实数据库和图片持久化、备份与恢复；不把演示环境的临时目录作为长期存储 |

CatVTON、OOTDiffusion、IDM-VTON 当前采用非商业许可，商业接入需要另外取得授权。许可条件未满足时，相关条目保持待评估，不进入商业产品开发。

## 7. 交付批次与进入条件

| 推进顺序 | 需求范围 | 这一批的交付物 | 进入下一批的条件 |
| --- | --- | --- | --- |
| **第 1 批：基础可复用** | P0-01、P0-02 | 可恢复的数据与共用业务函数 | 旧数据和原有功能回归通过，身份检查一致 |
| **第 2 批：付费与任务可靠** | P0-03 至 P0-06 | 防重复生成、恢复、预算和服务端授权 | 网络异常、并发、重启、越权和预算场景通过 |
| **第 3 批：自动推荐可用** | P1-01 至 P1-05 | “帮我搭配”、有效方案卡片、保存与试穿连接 | 推荐真实、约束有效、连衣裙保存与试穿闭环通过 |
| **第 4 批：聊天 Agent 可用** | P1-06 至 P1-09 | 对话、工具循环、异步结果与完成检查 | 目标能执行和调整，只有真实结果才报告完成 |
| **第 5 批：批量建立衣橱** | P2-01 至 P2-03 | 多图导入、逐项审核和失败项处理 | 部分失败与重复请求不污染正式衣橱或重复付费 |
| **第 6 批：个性化增强** | P2-04 至 P2-06；P2-07 可选 | 可管理偏好、推荐反馈及按需天气辅助 | 长期／临时要求区分正确，当前指令和删除行为生效 |
| **条件批次：扩展能力** | 被触发的 P3 条目 | 实测支持的新引擎或可靠的长期云部署 | 按对应触发条件和验收决定，不要求全部完成 |

同一批内可以准备不依赖其他项的内容；正式交付仍按前置依赖验收。P3-04 与试穿模型实验没有依赖关系，只在长期云使用需求成立时启动。

## 9. 暂不放入当前开发队列的需求

这些内容可以保留为想法，但没有明确需求时不加入当前依赖：

- 鞋包配饰、外套叠穿与更多身体槽位；需要先扩展衣物结构和试穿能力。
- 尺码测量、3D 人体与实时 AR 试穿。
- 商城、支付、购物车、订单和退款。
- 每日主动推送、定时自治推荐及对外消息发送。
- Agent 团队、子 Agent、通用任务依赖图和独立 MCP 服务。
- 为少量本地衣物引入向量数据库、Redis 或多服务架构。
- 在基本验收尚未建立时，用另一个模型替代真实结果检查。

这些想法只有出现具体目标、必要性和可验证结果后，才转成新的排期需求。

## 10. 需求完成与排期更新规则

一项需求只有满足以下条件，才能标记为“已完成”：

- 用户能实际使用对应功能，或基础能力已经被相应路径调用。
- 前置依赖和相关数据迁移完成。
- 正常路径与必要异常路径验证通过，原有相关功能没有回退。
- 权限、费用、副作用和恢复状态与界面提示一致。
- 操作说明与验收结果可以查阅。

真实模型联调要在有效凭证与已授权费用范围内进行；权限、重复请求、提交未知和恢复等异常优先用模拟服务验证。平台实际账单与应用费用估算分别记录。

执行时使用以下状态即可：

**待开发 → 开发中 → 待验收 → 已完成**

缺少输入或外部条件时标为“待条件满足”，记录具体原因和未完成部分。调整优先级时同步修改需求依赖与交付批次；不以已经开始、接口已返回、任务已排队或模型声称成功代替验收完成。
